## BL-03 — Powtarzalne próby na prawdziwym modelu w szablonie

Funkcje potwierdzone w AgenticApp wyłącznie historycznym przebiegiem lub ręczną sondą, bez dowodu wykonywanego na kodzie szablonu. Trzeba je powtórzyć w szablonie i utrwalić jako powtarzalny, izolowany test lub skrypt odbiorowy z zapisem wersji i wyniku.

**Warunek zamknięcia:** każde kryterium pakietu ma dowód z przebiegu na commicie szablonu (test e2e z modelem lub skrypt odbiorowy z logiem), oznaczony jako rzeczywisty model, z kontrolą negatywną tam, gdzie wymaga jej treść kryterium.

## BL-04 — Uwierzytelnienie subskrypcyjne i limity — próby graniczne

Zachowanie przy wygaśnięciu i odświeżeniu tokena, odrzuconym odświeżeniu, odwołanym logowaniu i limicie użycia, sprawdzone na granicy adaptera aż do widocznego UI, bez niszczenia poświadczeń użytkownika i bez przedstawiania symulacji jako rzeczywistego limitu.

**Warunek zamknięcia:** kontrolowane stand-iny na granicy adaptera SDK dają rozróżnialne stany w UI i zachowują historię bez powtórki mutacji; dowód oznaczony jako symulacja; opis odczytu poświadczeń zgodny z kodem.

| ID | Wymaganie | Stan | Brak |
|---|---|---|---|
| L8.2 | Działa uwierzytelnienie subskrypcyjne, z potwierdzeniem trybu bez ujawniania tokena. | częściowe | Żaden test nie potwierdza, że SDK użyło OAuth subskrypcji: apiKeySource z sesji SDK nie jest odczytywane, a po udanym przebiegu nie jest asercjonowany stan access=verified ani plan z poświadczenia; asercja w e2e/app.spec.ts przechodzi także bez logowania. |
| L8.3 | Klucz API Anthropic, gateway i automatyczny fallback płatnego API nie są aktywną ścieżką wykonania. | częściowe | Polityka opiera się tylko na czyszczeniu zmiennych środowiska: logowanie CLI kontem z kluczem API (ApiKeySource '/login managed key' w SDK 0.3.270) nie jest w kodzie wykluczone ani wykrywane, bo runtime nie sprawdza apiKeySource sesji; brak próby z ustawionym kluczem pokazującej, że przebieg nadal idzie przez subskrypcję. |
| L8.6 | Wygaśnięcie uwierzytelnienia i wyczerpanie limitu dają czytelny błąd oraz zachowują stan pracy. | częściowe | Błąd wygasłego lub odwołanego logowania nie jest przeprowadzony przez runtime do GUI (brak scenariusza serwera skryptowego); czytelna podpowiedź (wykonaj /login, poczekaj) jest tylko w Ustawieniach i nie jest sprawdzana testem, czat pokazuje surowy komunikat SDK z kodem. |
| L8.7 | Poświadczenia pozostają poza frontendem, artefaktami i logami. | częściowe | Nie przeszukano artefaktów i magazynu plików, run_events ani logów serwera po rzeczywistym uruchomieniu agenta; sandboxSettings nie blokuje odczytu katalogu ~/.claude, a Read jest auto-zatwierdzany, i nie sprawdzono, czy agent może odczytać poświadczenie i opublikować je jako artefakt. |
| L8.8 | Zgodność konkretnej wersji SDK, adaptera i sposobu logowania została sprawdzona rzeczywistym wywołaniem. | częściowe | Sposób logowania użyty przez SDK w tych przebiegach nie jest rejestrowany ani asercjonowany (apiKeySource, access.state), a wersje nie trafiają do wyniku testu; zgodność trójki SDK–adapter–logowanie wynika z założenia o środowisku, nie z zapisanego dowodu. |
| L8.9 | Sposób logowania, stan metadanych i ostatni potwierdzony dostęp są odrębnymi informacjami; obecność pliku nie oznacza zdrowego połączenia. | częściowe | Pasek stanu (AppShell StatusBar) pokazuje zieloną kropkę i napis subskrypcja przy obecnym pliku, gdy dostęp jest unverified lub failed, więc obecność pliku nadal wygląda jak zdrowe połączenie; stan dostępu jest globalny w procesie i nadpisywany przez każdy nieanulowany błąd uruchomienia (także sandbox i timeout), a method jest stałą. |
| L8.10 | Przeterminowany access token nie blokuje automatycznie możliwości odświeżenia przez SDK; skuteczne i odrzucone odświeżenie mają sprawdzone zachowanie. | częściowe | Nie sprawdzono skutecznego odświeżenia (przeterminowane poświadczenie → udany przebieg → access verified i nowy termin) ani odrzuconego odświeżenia przez runtime do czatu i Ustawień; komunikat odmowy to założony tekst, niepotwierdzony dla SDK 0.3.270. |
| L8.11 | Limit użycia jest odróżniany od odwołanego logowania, błędu sieci i błędu narzędzia; zachowuje historię i nie powoduje automatycznej powtórki mutacji. | częściowe | Brak próby, w której mutacja przez narzędzie poprzedza limit, z asercją jednego skutku i braku powtórki; klasyfikacja opiera się na podciągach komunikatu (np. 429, credential, authenticat) niepotwierdzonych na rzeczywistych błędach SDK, więc inny błąd sieci może zostać uznany za limit lub odwołanie. |

## BL-07 — Trwałość, kopia i migracje

Pozostaje jedno pytanie, na które nie da się odpowiedzieć bez tury modelu: którą z dwóch reakcji daje prawdziwy SDK, gdy transkrypt wznawianej sesji nie istnieje. Obie ścieżki są obsłużone i sprawdzone stand-inem na granicy adaptera; kopia z WAL, próba migracji sprzed każdej migracji platformy i odtworzenie są przećwiczone w szablonie na danych syntetycznych (Z2, 2026-09-18).

**Warunek zamknięcia:** jedna próba na prawdziwym modelu: rozmowa z sesją, usunięcie jej transkryptu, kolejne polecenie — zapisany komunikat SDK rozstrzyga, która ścieżka zachodzi, i potwierdza albo uzupełnia wzorce rozpoznawania w isMissingSessionTranscript.

| ID | Wymaganie | Stan | Brak |
|---|---|---|---|
| L7.13 | Brak transkryptu SDK dla zachowanej rozmowy daje jawny wynik odzyskiwania lub błąd; aplikacja nie deklaruje zachowania pamięci, której nie odtworzyła. | częściowe | Nie sprawdzono na prawdziwym SDK, którą z dwóch reakcji daje faktycznie brak transkryptu (odmowa wznowienia czy cicha nowa sesja) — zadanie nie miało budżetu tur, a przypadku nie da się wywołać bez usunięcia transkryptu prawdziwej sesji; rozpoznanie opiera się na wzorcach komunikatów, więc nieznane brzmienie z nowszej wersji SDK wpadnie w integration_failed zamiast we własny kod. Dla ścieżki „cicha nowa sesja” jawny wynik to zdarzenie, wpis w run_events i ostrzeżenie serwera — uruchomienie celowo nie jest przerywane (przerwanie przy hipotetycznym rozwidlaniu sesji przez SDK zepsułoby każdą kontynuację), więc użytkownik nie widzi wtedy komunikatu w wątku. |

## BL-08 — Czat, zdarzenia i historia

Braki w dowodzie lub implementacji po stronie gotowego czatu, AG-UI i projekcji historii, które nie należą do innych pakietów.

**Warunek zamknięcia:** każde kryterium pakietu ma test GUI lub test kontraktu w regresji szablonu, a ograniczenia biblioteki są potwierdzone dla użytej wersji i obsłużone albo jawnie niespełnione.

| ID | Wymaganie | Stan | Brak |
|---|---|---|---|
| L4.3 | Rozmowy mają automatyczne sensowne tytuły oraz możliwość zmiany tytułu; mechanizm nie korzysta z API Anthropic. | częściowe | Zmiana tytułu nie jest dostępna użytkownikowi: menu wiersza gotowego ThreadList (@openuidev/react-ui 0.13.10) ma tylko Delete, aplikacja nie dodaje własnej kontrolki, a endpoint PATCH nie ma testu. Skutek: możliwość zmiany tytułu istnieje tylko w API i nie ma dowodu. |
| L4.5 | Przełączenie rozmowy nie miesza wiadomości, kontekstu ani wyników trwających wykonań. | częściowe | e2e/background-tasks.spec.ts „praca w rozmowie B nie miesza sie z zadaniem w A” nie ma trwającego zadania A (instancja skryptowana jest zatrzymywana po poprzednim teście, co przerywa wykonanie), więc równoległa praca A i B w GUI nie jest wykazana. Kontekst następnego polecenia po przełączeniu nie jest sprawdzany; analiza kodu: selection w useAppState nie jest czyszczone przy zmianie rozmowy ani przestrzeni i trafia do kolejnego polecenia. |

Brak testu powtórzonego POST. |
